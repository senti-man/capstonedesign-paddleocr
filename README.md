# 📁 개인정보 마스킹 시스템 - OCR 기반 파일 자동 마스킹

이 프로젝트는 이메일 첨부파일로 전송되는 PDF, 이미지, 엑셀 파일 내 개인정보(이름, 주민등록번호, 주소 등)를 자동으로 탐지하고,
사용자가 선택한 항목만 마스킹 처리한 후, 다시 Gmail에 업로드하는 **크롬 확장 프로그램 + Flask 백엔드** 기반 시스템입니다.

---

## ✅ 기능 요약

- 📄 OCR 결과(JSON)를 받아 민감 정보 탐지
- ✅ 사용자가 선택한 항목만 마스킹 (텍스트 대체 / 박스 선택 가능)
- 📁 이미지, PDF, Excel 파일 포맷 지원
- 🔗 Gmail에 첨부된 파일 자동 분석 및 마스킹 후 재업로드

## 🗂️ 프로젝트 구조

```
masking_module/
├── config.py                 # 정규표현식 패턴 설정
├── detector.py              # 개인정보 탐지 함수
├── pdf_text_extractor.py    # PDF 텍스트 레이어 판별 및 직접 추출 (OCR 우회)
├── mask_image.py            # 이미지 마스킹 (텍스트 or 박스 스타일)
├── mask_pdf.py              # PDF 마스킹 (OCR 경로: 이미지 변환 후 처리 / 텍스트 경로: 벡터 리댁션)
├── mask_excel.py            # 엑셀 마스킹 처리
├── server.py                # Flask 서버 (확장프로그램과 연동)
├── utils/
│   └── ocr_converter.py     # OCR 결과를 마스킹 포맷으로 변환
├── uploads/                 # 업로드된 원본 파일
├── processed/               # 마스킹 완료된 결과 파일
```

### 🔀 하이브리드 PDF 처리

`server.py`의 `/upload`는 PDF 업로드 시 `pdf_text_extractor.has_extractable_text()`로 텍스트 레이어 존재 여부를 먼저 판별한다.

- **텍스트 레이어 있음** (일반 문서 PDF): `pdf2image`/OCR을 거치지 않고 `extract_pdf_ocr_format()`으로 텍스트·좌표를 직접 추출한다. 마스킹 시에는 `mask_pdf.mask_text_pdf_from_ocr()`가 `PyMuPDF`의 `add_redact_annot` + `apply_redactions`로 원본 벡터 PDF에서 해당 영역의 텍스트 자체를 제거한다(박스 이미지 덧씌우기가 아닌 진짜 리댁션). 래스터화를 하지 않으므로 OCR 호출 비용과 좌표 변환 오차가 없다.
- **텍스트 레이어 없음** (스캔 이미지 PDF): 기존과 동일하게 `pdf2image` → PaddleOCR → `mask_pdf.mask_pdf_from_ocr()` 경로를 사용한다.

### 🎯 정밀 마스킹 (줄 전체가 아니라 탐지된 문자열만)

원래는 OCR/텍스트 추출이 "줄" 단위로 이루어져서, 한 줄에 탐지 항목이 하나라도 있으면 줄 전체가 검은 박스로 가려졌다(예: "서울특별시 강남구 테헤란로 123"에서 "강남구"만 선택해도 줄 전체가 사라짐). 이제는 탐지된 문자열 부분만 정밀하게 가린다.

- **텍스트 PDF**: `mask_text_pdf_from_ocr()`가 `page.search_for(선택된_문자열)`로 그 문자열이 실제로 위치한 정확한 좌표를 찾아 그 부분만 리댁션한다. 벡터 PDF는 실제 문자 위치 정보를 그대로 가지고 있어서 근사치가 아니라 정확하다. 이전의 줄 단위 좌표(`ocr_json`) 자체가 필요 없어져서 함수 시그니처에서 뺐다.
- **이미지/스캔 PDF**: OCR은 줄 단위 좌표만 주기 때문에 완전히 정확할 수는 없다. `utils/ocr_converter.estimate_sub_bbox()`가 줄 전체 글자 수 대비 매칭된 문자열의 시작/끝 위치 비율로 가로 폭을 추정한다 — 글자마다 실제 폭이 달라(한글/영문/숫자 혼용 등) 완벽하지 않은 근사치이지만, 줄 전체를 가리는 것보다는 훨씬 정밀하다. 못 찾으면 안전하게 원래 줄 전체 박스로 폴백한다(과소 마스킹보다 과다 마스킹이 낫다는 원칙).

### 🖼️ 텍스트 PDF 안에 박힌 이미지도 보완 OCR (중요한 미탐 수정)

**발견된 문제**: 하이브리드 PDF 처리는 `has_extractable_text()`가 True면 전체 문서를 "텍스트 전용, OCR 없음" 경로로 보낸다. 그런데 텍스트가 많은 문서라도 특정 페이지에 신분증 사진·스크린샷·스캔본 같은 **이미지가 통째로 박혀 있으면**, 그 이미지 속 텍스트는 `page.get_text()`로 전혀 추출되지 않는다 — 실제로 `uploads/test.pdf`의 마지막 페이지(주민등록증 이미지, 텍스트 0자)가 이 문제로 주민등록번호를 통째로 놓치고 있었다.

`pdf_text_extractor.extract_embedded_images()`가 각 페이지의 삽입 이미지(`page.get_images()`)를 찾아 픽셀 데이터 + 페이지 상 배치 좌표를 반환하면, `/upload`에서 그 이미지들에 OCR을 돌려 결과를 페이지 좌표계로 변환해 병합한다(이미지 픽셀 좌표 → 이미지가 배치된 rect 비율로 환산). 아이콘·로고 같은 작은 이미지(40px 미만)는 제외해서 불필요한 OCR을 줄인다. 이렇게 보완된 항목은 `_from_image` 플래그를 달아두고, 마스킹 시 `mask_text_pdf_from_ocr()`의 `image_derived_fields` 인자로 좌표 기반 리댁션한다(실제 텍스트 레이어에 없어서 `search_for`로는 못 찾기 때문).

실측: `test.pdf`(텍스트 위주 7페이지, 마지막 페이지만 이미지)에서 이 보완 없이는 "주민등록번호" 카테고리 자체가 탐지 결과에 없었고, 적용 후 "913680-9136808"이 정확히 탐지·마스킹됨을 확인했다.

### 🪪 고유식별정보·금융정보 탐지 추가, 주소 부분 마스킹 버그 수정

**고유식별정보**(주민등록번호·여권번호·운전면허번호·외국인등록번호)와 신용카드번호·계좌번호를 `config.py`(`MASKING_CONFIG`)에 추가했다.

- **여권번호**: `[MSROD]\d{8}` 및 2020년 이후 신형(`[MSROD]\d{3}[A-Z]\d{4}`) — 출처: [Microsoft Purview "대한민국 여권 번호" 민감정보 유형 정의](https://learn.microsoft.com/ko-kr/purview/sit-defn-south-korea-passport-number)
- **운전면허번호**: 지역코드(11~19, 20~26, 28만 유효)+연도 2자리+일련번호 6자리+검증코드 2자리, 하이픈 선택적 — 출처: [Microsoft Purview "대한민국 운전면허증 번호" 민감정보 유형 정의](https://learn.microsoft.com/ko-kr/purview/sit-defn-south-korea-drivers-license-number)
- **외국인등록번호**: 주민등록번호와 자릿수·하이픈 형식이 동일해서(뒷자리 성별 코드만 다름) 기존 주민등록번호 패턴이 이미 커버한다.
- **신용카드번호**: 국내 표준 16자리(4-4-4-4)와 Amex 15자리(4-6-5, 34/37로 시작).
- **계좌번호**: 은행마다 자릿수·구분이 제각각이라(국민 6-2-6, 신한 3-3-6, 우리 4-3-6 등) 정규식만으로 완벽히 특정하기 어렵다. "하이픈으로 나뉜 숫자 그룹 3~4개"라는 공통 특징으로 넓게 잡되, **날짜(YYYY-MM-DD)와 전화번호 형식은 명시적으로 제외**했다 — 처음 버전은 이 예외 처리가 없어서 "2026-03-05" 같은 날짜가 계좌번호로 오탐됐다. 계좌번호는 다른 항목보다 오탐·미탐이 둘 다 크다는 한계가 있다.

**주소 부분 마스킹 버그**: 최하은 신분증 테스트에서 주소가 일부만 가려지는 문제를 발견해 원인을 추적했다.

1. 도로명 패턴(`OO로/길 + 숫자 + 번길`)이 건물번호(예: "장안로123번길 **45**")를 포함하지 않아, 번지수만 그대로 노출됐다. 패턴 끝에 건물번호를 선택적으로 포함하도록 확장했다.
2. 위를 고치는 과정에서 새로 발견한 문제: OCR 인식 결과는 "번길45"처럼 공백 없이 붙어 나올 때가 있는데, 패턴에 공백을 필수로 넣으면 그 경우 정규식의 단어 경계(`\b`)가 성립하지 않아 **매치 자체가 통째로 실패**했다. 건물번호 앞 공백도 선택 처리해서 해결했다.
3. 같은 이유로 "101동202호"처럼 동/호수가 붙어 나오면 "202호"가 아예 안 잡히는 문제도 발견해, 해당 패턴의 불필요한 단어 경계를 제거했다.

실측(신분증 이미지): 주소 3줄이 부분적으로만 가려지던 것에서, "경기도수원시장안로123번길45", "101동", "202호", "장안동", "해피아파트"까지 전부 정확히 마스킹되는 것을 확인했다.

### 🔍 OCR 엔진: PaddleOCR (로컬, 무료)

원래 Naver Clova OCR API를 사용했으나, API 키가 `server.py`에 하드코딩된 채로 GitHub에 공개되면 타인이 이 키로 호출한 비용이 프로젝트 소유자에게 청구되는 문제가 있어 **PaddleOCR로 완전히 교체**했다 ([paddle_ocr.py](masking_module/paddle_ocr.py)).

- 네트워크 호출도, API 키도 없음 → 비용/키 유출 리스크가 구조적으로 사라짐
- `korean_PP-OCRv5_mobile_rec`(한글 인식 모델) + `PP-OCRv5_mobile_det`(검출 모델) 조합, 모델 가중치는 최초 실행 시 `~/.paddlex/official_models/`에 자동 다운로드되어 캐시됨 (인터넷 필요, 이후로는 오프라인 동작)
- `clova_ocr.py`는 더 이상 기본 경로에서 사용되지 않지만 참고용으로 남겨둠

### ⚡ 스캔 이미지 PDF 다중 페이지 병렬 처리

텍스트 레이어가 없는 PDF는 페이지마다 OCR을 돌려야 해서 페이지 수에 비례해 느려진다(모바일 모델 기준 페이지당 약 20초). PaddleOCR 인스턴스는 스레드 세이프하지 않아 스레드로는 병렬화할 수 없으므로, `run_paddle_ocr_parallel()`([server.py](masking_module/server.py))이 `ProcessPoolExecutor`로 완전히 독립된 프로세스에 페이지를 나눠 돌린다 — 프로세스마다 메모리가 분리돼 있어 동시 호출이 안전하다. 기본 워커 수는 4개(메모리 사용량 고려, 프로세스마다 모델 사본을 새로 로드함).

실측(6페이지 스캔 이미지 PDF, 4 workers): 순차 140.6초 → 병렬 77.6초 (약 1.8배 단축). 프로세스마다 모델을 새로 로드하는 오버헤드 때문에 코어 수만큼 선형적으로 빨라지지는 않는다. 페이지가 1장뿐이면 병렬화 오버헤드가 더 커서 자동으로 순차 처리로 전환된다.

CPU 코어가 많다면 `run_paddle_ocr_parallel(image_paths, max_workers=8)`처럼 워커 수를 늘려볼 수 있으나, 워커마다 모델을 메모리에 새로 올리므로 메모리 여유를 고려해서 조정한다.

## 🛠️ 설치 방법 (VSCode 기준)

### 1️⃣ 가상환경 생성 및 패키지 설치

PaddlePaddle은 아직 Python 3.14용 배포판이 없어 **Python 3.12**를 사용해야 한다.

```bash
cd masking_module
py -3.12 -m venv .venv
.venv\Scripts\pip install -r requirements.txt
```

VSCode에서 이 폴더(`capstonedesign`)를 열면 `.vscode/settings.json`이 `masking_module/.venv`를 인터프리터로 자동 지정한다. Command Palette → `Python: Select Interpreter`에서 `.venv`가 안 잡혀 있으면 수동으로 선택한다.

### 2️⃣ Poppler (PDF→이미지 변환, 스캔 PDF OCR 경로에만 필요)

시스템 PATH를 건드리지 않기 위해 poppler 바이너리를 프로젝트 폴더 안에 직접 둔다. `masking_module/poppler/Library/bin/`에 `pdftoppm.exe`가 위치하도록 [Poppler for Windows Releases](https://github.com/oschwartz10612/poppler-windows/releases)에서 zip을 받아 풀면 되고, `config.py`의 `POPPLER_PATH`가 이 경로를 자동으로 읽는다(없으면 시스템 PATH로 폴백). 텍스트 레이어가 있는 PDF는 이 단계 없이도 동작한다.

- **원본 파일이 삭제되지 않고 마스킹본과 함께 남는 문제 (미해결, 알려진 한계)**: 파일 선택 이벤트를 캡처 단계 + `stopImmediatePropagation()`으로 가로채 Gmail이 원본을 아예 못 보게 막는 방식을 시도했으나, 실제 Gmail에서 감지 자체가 완전히 동작하지 않는 회귀가 발생해 v1.4에서 롤백했다(추정 원인: Gmail도 캡처 단계에서 더 먼저 등록된 자체 리스너로 이벤트를 처리하고 있어, 감지 코드가 아예 실행되지 못한 것으로 보인다 — 실제 Gmail 없이는 확정 검증이 어렵다). 감지가 안정적으로 동작하는 것을 우선해 예전 방식(버블 단계 감지)으로 되돌렸고, 그 결과 원본 중복 첨부 문제는 다시 남아있다. 더 안전한 대안(마스킹 완료 후 원본 첨부 칩을 찾아 제거하는 방식 등)은 추후 별도로 검증해야 한다.
- **페이지 많은 PDF 마스킹 "실패" 버그 수정**: 마스킹 완료를 기다리는 폴링이 최대 40초로 고정돼 있어서, 페이지가 많아 처리 시간이 길어지면 서버는 계속 작업 중인데 클라이언트가 먼저 시간 초과로 포기했다. 최대 10분(200회 × 3초)까지 기다리도록 늘리고, 대기 중 경과 시간을 로딩 메시지에 표시하도록 개선했다.

- **전송 시점 강제 차단**: 개인정보가 감지됐는데 마스킹/수정하지 않은 첨부파일이나 본문 텍스트가 남아있으면 Gmail "보내기" 클릭 자체를 가로막고 경고 배너를 띄운다. 위험 요소가 없으면 아무 것도 하지 않고 그대로 통과한다.
- **다중 파일 버그 수정**: 예전엔 마스킹을 취소하면 그 첨부파일이 통째로 사라졌다(`input.files`를 마스킹된 파일들로만 교체했기 때문). 이제는 원본이든 마스킹본이든 파일 개수가 항상 1:1로 유지된다.
- **드래그앤드롭 첨부 감지**: 기존엔 파일 선택창으로 첨부할 때만 감지했다. 이제 드롭 이벤트도 캡처해서 같은 탐지·마스킹 파이프라인을 태운다 (Gmail 작성창 내부에 숨겨진 file input이 있다는 전제의 best-effort 구현).
- **본문 텍스트 검사**: 작성 중인 본문(contenteditable)에 입력을 멈추면(디바운스 900ms) `/detect_text`로 개인정보 패턴을 검사해 조용한 경고 배너를 띄운다. 매 키 입력마다 다이얼로그를 띄우진 않고, 실제 차단은 "보내기" 시점에만 수행한다.
- **받은 메일 첨부파일 마스킹**: 수신 메일의 다운로드 버튼(`aria-label`에 "다운로드/download" 포함)을 클릭하면 파일을 가져와 탐지·마스킹 후 마스킹된 버전만 다운로드시킨다. 다운로드 링크를 동기적으로 찾지 못하면 아무 것도 가로채지 않고 Gmail 기본 동작에 맡긴다 (오탐으로 정상 다운로드를 막지 않기 위함) — Gmail 수신함 DOM 구조는 확인 없이 만든 best-effort 구현이라, 실제 동작이 다르면 `isDownloadControl`/`findDownloadUrl`을 점검해야 한다.
- **팝업 통계**: 확장 아이콘 클릭 시 누적 감지/마스킹/전송 차단 건수를 보여준다 ([popup.html](chrome_extension/popup.html), [popup.js](chrome_extension/popup.js)). 배지에는 현재 작성창의 미해결 위험 항목 개수가 실시간으로 표시된다.
- **UX**: 네이티브 `confirm()`/`alert()` 대신 스타일이 적용된 배너/토스트로 교체.
- **받은 메일 피싱 의심도 검사**: 메일 목록 항목(`role="listitem"`)을 클릭해 열람하면 본문·링크를 모아 규칙 기반 스코어러([phishing_detector.py](masking_module/phishing_detector.py))로 검사하고, "주의"/"위험" 판정 시 근거 규칙과 함께 배너로 표시한다.

### 🎣 피싱 탐지 설계 근거

정규식 기반 개인정보 탐지(`detector.py`)와 마찬가지로, 피싱 탐지도 학습 데이터 없이 **규칙 기반 + 차등 가중치 점수제**로 설계했다.

- Basnet, Sung, Liu, *"Rule-Based Phishing Attack Detection"*, New Mexico Tech — 15개 규칙(URL 구조·블랙리스트·콘텐츠 기반)을 Decision Tree/Logistic Regression으로 학습해 **정확도 99%, FPR 0.5%, FNR 2.5%**를 달성했고, 단순 "규칙 개수 카운트 + 임계값" 방식만으로도 임계값 4에서 **TPR 91.87%, FPR 1.80%**를 보고했다. 이 프로젝트는 외부 API(검색엔진, 블랙리스트)를 쓰는 규칙은 제외하고, 이메일 본문·링크만으로 판단 가능한 규칙(IP 기반 URL, URL 난독화, `@` 도메인 위장 등)만 차용했다.
- 위 논문의 Logistic Regression 계수 분석에서 규칙별 위험도(Odds Ratio)가 크게 다름을 확인했고 — IP 기반 URL이 가장 강한 단일 지표(97% 이상 자체 탐지) — 이를 근거로 이 프로젝트는 동일 가중치 대신 **HIGH(10)/MEDIUM(5)/LOW(2)** 3단계 차등 가중치를 사용한다(하이브리드 휴리스틱-ML 논문들에서 흔히 쓰이는 티어 방식).
- 등급(안전/주의/위험) 판정은 순수 백분율 임계값이 아니라, 위 논문이 보인 "강신호 규칙 단독으로도 충분"이라는 관찰에 따라 **HIGH 등급 규칙이 하나라도 매칭되면 즉시 "위험"**으로 판정하고, 약한 규칙들은 여러 개가 겹쳐야(4개 이상) "위험"으로 올라가도록 설계했다.

**자체 검증 결과** (직접 제작한 표본 10건 — 피싱 4건, 정상 6건 — 대량 데이터셋 기반 통계가 아닌 설계 검증용 소규모 테스트):

| 구분 | 건수 | 정확히 판정 | 비율 |
|---|---|---|---|
| 피싱 메일 → "위험" 판정 | 4건 | 4건 | 100% |
| 정상 메일 → "안전" 판정 (경계 사례 2건 포함*) | 6건 | 6건 | 100% (오탐 0건) |

\* 경계 사례: "비밀번호를 변경하시려면 설정에서 진행해주세요"(민감정보 요구 문구처럼 보이지만 정상 안내문), 실제 은행 공식 도메인으로 온 정상 알림 메일. 초기 구현에서는 첨부파일명("sample_pii.png")의 마침표를 URL 도메인으로 오인식해 정상 메일을 오탐하는 버그가 있었고, 표시 텍스트가 `http(s)://`/`www.`로 시작할 때만 링크로 인정하도록 수정해 해결했다.

## 🛠️ 문제 해결

### Gmail에서 첨부해도 탐지 팝업 없이 그냥 원본이 첨부됨

`https://mail.google.com`(공개 사이트)에서 `http://127.0.0.1:5000`(사설 네트워크)로 보내는 요청은 크롬의 **Private Network Access** 정책 때문에 프리플라이트 단계에서 기본 차단된다. `masking_module` 서버 쪽 로컬 테스트(`http://localhost`끼리)에서는 재현되지 않고 실제 Gmail에서만 나타나는 문제라 발견하기 까다로웠다.

`server.py`에서 `CORS(app, allow_private_network=True)`로 해결했다 (flask-cors 6.x 필요). 이 옵션 없이 직접 `Access-Control-Allow-Private-Network` 헤더를 수동으로 추가하면 flask-cors가 같은 헤더를 자체적으로도 추가해서 값이 중복(`true`+`false`)되어 오히려 크롬이 거부하니 주의.

브라우저 개발자 도구(F12) → Console/Network 탭에서 `Private Network Access` 또는 `blocked`로 시작하는 에러가 보이면 이 문제다.

### 이름/주소 오탐이 많음 (논문·보고서 등 산문 위주 문서)

`detector.py`의 이름 탐지 정규식은 "[성씨 13종]으로 시작하는 2~3글자 단어"를 전부 후보로 잡기 때문에, 산문이 많은 문서에서는 "이용해", "정교한", "한다면" 같은 흔한 동사·형용사까지 대량으로 오탐된다(주소의 "OO동" 패턴도 "자동", "수동"처럼 우연히 "동"으로 끝나는 흔한 단어를 오탐). 실제 캡스톤 보고서 PDF(31페이지)로 테스트했을 때 69건 탐지 → 접두어 기반 예외 필터 추가 후 16건으로 줄었고, 남은 16건 중 14건은 실제 인명(팀원명·인용 저자명)이었다.

**오탐을 줄이려던 예외 필터가 반대로 미탐을 만든 사례**: `EXCLUDED_NAME_PREFIXES`에 "이용"을 접두어로 넣었더니 "이용해"(동사)는 걸러졌지만 실제 팀원 이름 "이용운"까지 같이 걸러졌다. **마스킹 도구는 오탐(체크박스 하나 더 뜨는 것)보다 미탐(실제 개인정보를 놓치는 것)이 훨씬 위험**하므로, 실제 이름과 충돌 여지가 있는 접두어(이용, 최종 등)는 접두어 방식에서 빼고 관찰된 정확한 활용형만 개별 등록하는 방식(`EXTRA_EXCLUDED_NAME_EXACT`)으로 바꿨다.

또 "서재현"처럼 기존 성씨 13종(김이박최정강조윤장유임한홍)에 없는 성씨는 애초에 후보에도 안 잡히는 미탐이 있었다. 성씨를 무작정 늘리면(서·신·권·황·송·전·고·문·양·손·배·허·남 추가 테스트) "서버", "문서", "전송"처럼 흔한 단어와 충돌해 오탐이 16건→49건으로 폭증해서 되돌렸다. 대신 **"OOO 교수님/박사님/기자/대표" 등 호칭이 바로 뒤따르면 성씨 목록과 무관하게 이름으로 인식**하는 보완 규칙을 추가했다 — 오탐 증가 없이 "서재현"(지도교수) 미탐을 해결했다(다만 "지도교수"를 "지도"+교수 호칭으로 잘못 쪼개는 부작용이 있어 "지도"를 예외 처리했다). 최종 결과: 16건 → 18건(새로 잡힌 서재현·이용운 2건만 순수 추가, 다른 오탐 증가 없음).

`EXCLUDED_NAME_PREFIXES`/`EXCLUDED_DONG_WORDS`(둘 다 `detector.py`)에 흔한 오탐 단어의 2글자 어간을 등록해두면 정확 일치가 아니라 그 어간으로 시작하는 모든 활용형이 한 번에 걸러진다. 다만 이는 **근본 해결이 아니라 대증 요법**이다 — "이용해"(동사)와 "이민석"(이름)을 정규식만으로 구분하는 것은 원리적으로 불가능하며, 진짜 해결은 형태소 분석/개체명 인식(NER) 도입이 필요하다(보고서 6.3절 "머신러닝 기반 탐지 방식 병행"과 동일한 결론). 오탐이 남아있는 상황에서 특정 항목만 빼고 싶을 때는 마스킹 다이얼로그의 전체 선택/해제·카테고리별 선택/해제 버튼을 활용한다.

### 마스킹이 "무한 로딩"처럼 되다가 몇 분 뒤 실패로 뜸 (서버 코드는 멀쩡한데도)

**원인은 서버가 여러 개 켜져 있는 것이다.** `server.py`를 껐다 켰다를 반복하면서 이전 프로세스가 완전히 종료되지 않으면, Windows에서는 여러 `python.exe` 프로세스가 동시에 포트 5000을 리슨하는 상태가 될 수 있다. 이러면 `/mask` 요청은 프로세스 A가 받아 처리하는데, 그 다음 완료 여부를 확인하는 `/result` 폴링 요청은 OS가 프로세스 B로 보내버릴 수 있다 — masking_status 딕셔너리는 프로세스별 메모리 상태라 B는 그 파일에 대해 아무것도 모르므로, 실제로는 A가 이미 처리를 끝냈어도 클라이언트는 영원히 "처리 중"만 받다가 결국 시간 초과로 실패한다.

**확인 방법** (PowerShell):
```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where-Object { $_.CommandLine -like '*server.py*' } | Select-Object ProcessId, CommandLine
```
2개 이상 나오면 이 문제다. 전부 종료 후 서버를 **딱 하나만** 다시 켠다:
```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where-Object { $_.CommandLine -like '*server.py*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```
(작업 관리자에서 `python.exe`를 전부 종료해도 된다.)

`app.run(debug=True, threaded=True, use_reloader=False)`로 바꿔서 ① 서버가 요청을 동시에 여러 개 처리할 수 있게 하고 ② 자동 재시작 감시자(reloader, 부모-자식 프로세스 구조라 종료가 꼬이면 좀비를 남기기 쉬움)를 꺼서 이런 상황 자체가 덜 생기게 했다. `process_masking()`에는 시작/완료/실패 시각과 소요 시간, 실패 시 전체 스택 트레이스를 로그로 남기도록 추가했다 — 다음에 비슷한 증상이 있으면 서버 터미널 로그로 정확히 어느 단계에서 멈췄는지 바로 확인할 수 있다.
